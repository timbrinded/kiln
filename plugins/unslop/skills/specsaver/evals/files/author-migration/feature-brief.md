# Brief: move `orders.status` from free text to an enum, online

Notes from Tuesday's whiteboard session, tidied up. Someone please turn this into the actual migration and rollout spec.

## Where we are and where we want to be

`orders.status` is `text NOT NULL`, about 48M rows, bigint `id` primary key. Since the 2021 normalisation fix the app only writes seven lowercase values: `pending`, `paid`, `packed`, `shipped`, `delivered`, `cancelled`, `refunded`. Rows older than that are messy. I ran the distinct query on the replica last night: mixed case (`Paid`, `SHIPPED`), trailing whitespace on roughly 300k rows, and about 2,100 rows spelt `canceled`. Nothing else. No NULLs, the constraint has always been there. Database side, the only thing that references `orders.status` is the partial index `orders_pending_idx ON orders (id) WHERE status = 'pending'` that the fulfilment queue uses; no views, triggers, foreign keys or check constraints (checked `pg_depend` and `\d+ orders` on the replica). We are on Postgres 14.

Target: an `order_status` enum type with those seven values, declared in the lifecycle order listed above so `ORDER BY state` sorts by lifecycle rather than alphabetically (the finance export is the only thing that sorts on status and Dan wants lifecycle order anyway), and a `state order_status NOT NULL` column. New name on purpose: we never rename a column while two app versions are live. `status` goes away at the end.

## Steps

Every deploy runs the old and new app versions side by side for a few minutes, so every step below has to work with the previous app version still running. `lock_timeout = 2s` on every migration statement; a schema statement that hits it fails and we look at why before rerunning it, the backfill has its own retry rule in step 3. "Error rate unchanged" in the checks means the orders service 5xx rate in Grafana for the 15 minutes after the deploy finishes is within 0.1 percentage points of the same 15 minutes the day before and Sentry shows no new issue group; anything else rolls the deploy back. The backfill checks replication lag on `replica-1` before every batch, pauses whenever it is over 5 seconds, polls every 10 seconds until it is back under, and if it has not recovered after 30 minutes stops with the progress row intact and posts in #orders-oncall.

1. Create the enum type, add `state` nullable with no default, metadata-only on 14. Also create `migration_progress (job text primary key, last_id bigint, max_id bigint, complete boolean, note text, updated_at timestamptz)`, which does not exist yet, and insert the `orders_state` row with `last_id = 0`; new table, so the lock rule is moot. Check: column and table exist, error rate unchanged.
2. Deploy app N+1: writes both `status` and `state` on every insert and update, still reads `status`. The old version ignores `state`, so the mix is fine; the one wrinkle (N updating `status` on a row N+1 already stamped, leaving `state` stale) is handled by the backfill predicate in step 3. Check: sample 1,000 rows written after the deploy, `state` populated on all of them.
3. Backfill, started only once version N is fully gone, so nothing is writing `status` alone any more. Batches of 5,000 rows, not id widths, deleted orders leave gaps: `SELECT max(id) FROM (SELECT id FROM orders WHERE id > last_id ORDER BY id LIMIT 5000) b` gives the upper bound `b`, then in one transaction `SELECT id, status FROM orders WHERE id > last_id AND id <= b AND mapped(status) IS NULL` (any rows: log the ids to the job output and `migration_progress.note`, stop before the UPDATE, so nothing in that batch is applied), then `UPDATE orders SET state = mapped(status) WHERE id > last_id AND id <= b AND state IS DISTINCT FROM mapped(status)`. `mapped(status)` is one inline SQL expression, `CASE lower(trim(status)) WHEN 'canceled' THEN 'cancelled' WHEN 'pending' THEN 'pending' ... ELSE NULL END::order_status`, spelt out for all seven. `IS DISTINCT FROM` rather than `IS NULL` because of the overlap wrinkle above: this predicate repairs stale rows, skips rows the dual write already has right, and Postgres re-checks it under the row lock, so the backfill and the app never fight. Stop at `max_id` snapshotted when the job starts; anything inserted after that came from N+1 and has `state` already. 200ms sleep between batches. `last_id` goes in `migration_progress` after each batch so a restart resumes rather than starting over. A lock timeout retries the same batch after 30 seconds, five times, then stops with the progress row intact and posts in #orders-oncall. Expect about five hours.
4. Verify on `replica-1`, each check one statement so it sees one snapshot and the dual write on the primary cannot make it flap: `count(*) WHERE state IS NULL` must be 0; `SELECT id FROM orders WHERE state IS DISTINCT FROM mapped(status)` must return no rows (full scan, a few minutes on the replica, and this is where the ids for any fix-up come from); per-value counts of `state` and of mapped `status` in a single `GROUP BY`, must match exactly. Then a random sample of 10,000 rows (`TABLESAMPLE SYSTEM (0.05)`, `LIMIT 10000`) showing `status`, mapped `status` and `state` side by side, zero mismatches, pasted into the ticket as the readable evidence.
5. First `CREATE INDEX CONCURRENTLY orders_state_pending_idx ON orders (id) WHERE state = 'pending'`, the `state` twin of `orders_pending_idx`; check `indisvalid` and that it is about the same size as the old one, otherwise the fulfilment queue falls off its index the moment reads switch. Then deploy app N+2: reads `state`, still writes both. Check: error rate unchanged, and rerun the step 4 checks after 24 hours.
6. `ADD CONSTRAINT orders_state_not_null CHECK (state IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT`, then `SET NOT NULL` (12+ uses the validated check to skip the scan under lock), then `DROP CONSTRAINT orders_state_not_null`, redundant once `NOT NULL` is on. Schema change: a redeploy does not undo it and it does not need undoing, everything from N+1 on writes `state`.
7. Drop `NOT NULL` from `status` so the next app version is allowed to stop writing it. Same story, a redeploy leaves it dropped and that is harmless.
8. Deploy app N+3: stops writing `status` and removes it from the ORM model and every query, so after this deploy no running code knows the column exists (there are no `SELECT *` or `RETURNING *` against `orders`; `git grep` for `orders.status` and the model field must come back empty before it ships). N+2 still writes both, that is fine.
9. Once N+3 is the only version running, same day as step 8: `DROP COLUMN status`, which takes `orders_pending_idx` with it. **This is the first irreversible step.** Everything before it can be undone by redeploying the previous app version, because the old column is always either intact or re-derivable from `state`; the constraint changes in steps 6 and 7 and the new index stay behind and stay true.

## Not decided yet

How long we sit in dual-write with reads on `state`, from step 5 to step 8, before dropping the old column. Steps 8 and 9 then run on the same day once N+3 is the only version live, so `status` is never stale for more than a working day and the soak really is the wait before the drop. I want at least one full billing cycle so the finance export has run against `state`; Dan thinks a week is plenty. This is the one open item and it needs a number before the spec is signed off.

## If something goes wrong

- Steps 1 to 4: roll back the deploy if there was one, drop `state`, the type and the `migration_progress` row. Nothing reads it yet. A half-finished backfill leaves a partly populated column plus the progress row, both harmless; usually we just resume from `last_id` rather than dropping.
- Step 4 mismatch: fix the mapping, rerun step 3 over the ids from the `IS DISTINCT FROM` scan (the predicate rewrites only the wrong rows, no need to null anything first), verify again.
- Steps 5 to 8: redeploy the previous app version. Both columns have complete data until step 8; after step 8 `status` can be rebuilt from `state` with the reverse mapping if we have to go back. The step 6 and 7 constraint changes and the new index stay in place, all harmless under any version from N+1 on.
- Step 9: restore from backup. There is no other way, which is the whole reason for the soak.

## Done means, and who runs it

`status` is gone and `orders_pending_idx` with it, `state` is `NOT NULL`, `orders_state_pending_idx` is valid, `git grep` finds no reference to `orders.status` in the app, the final step 4 check output is pasted in ORD-412, and the `migration_progress` row has `complete = true`.

Priya runs it, she owns the orders service, with whoever is on call as a second pair of eyes for steps 6 to 9. Every step's check output goes into ORD-412 as a comment before the next step starts. The backfill records its own progress in `migration_progress`.

## Out of scope

`order_events.status` is also free text, but that table is an append-only audit log of about 400M rows that nobody filters by status. Constraining it buys nothing and would roughly triple the backfill. Leave it.
